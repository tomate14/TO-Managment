# H1.3 Admin inicial — plan

**Historia:** Como responsable del sistema quiero que exista un admin al primer arranque para poder crear las demás cuentas.
- Al arrancar, si no existe ningún `ADMIN`, se crea uno con `ADMIN_EMAIL`, `ADMIN_PASSWORD` y `ADMIN_NAME` del `.env`.
- Si ya existe un admin, no se hace nada.

**Mockups:** no aplica (sin pantallas; es solo backend).

## Decisiones
- `InitialAdminProperties` (`app.initial-admin.*` ← `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME`, variables ya existentes en `.env`, `.env.example` y el compose), validadas con `@NotBlank`/`@Email`: si faltan, el backend no arranca.
- `InitialAdminService` (interfaz) + `InitialAdminServiceImpl`: devuelve un `InitialAdminOutcome` (enum con el mensaje de log y su nivel):
  - `CREATED`: no había admin; se crea con la contraseña hasheada con BCrypt y el email normalizado.
  - `ALREADY_PRESENT`: ya hay un admin (activo o no); no se hace nada.
  - `EMAIL_IN_USE`: no hay admin pero el email ya pertenece a otro usuario; no se crea nada y se avisa en el log (el backend arranca igual).
- `InitialAdminBootstrap` (`ApplicationRunner`) llama al servicio al arrancar y loguea el resultado **sin** email ni contraseña.
- Sin cambios de esquema: `supabase/init/*` no cambia. El admin no va en `02_seed.sql` porque sus datos son secretos del `.env`.
- `docs/dev/crear-usuario.md` explica el admin inicial.
- **Verificación:** se escriben los tests (unitario del servicio + integración del arranque), pero solo se verifica que compile.
